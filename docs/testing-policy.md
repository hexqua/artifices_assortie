# テスト設計・整理方針

Apprentice's Codex の `docs/testing-policy.md`（参照時のコミット `fa2367b26`）を基に、Artifices Assortie の新規開発へ適用する。既存テストの大規模整理、魔法固有の事例、他バージョンの保守手順は取り込まない。

この方針を最終形として固定しない。テストの分類、分割単位、実行方法に不都合が分かった場合は、理由を説明して関連方針も同じ変更で見直す。実行コマンド、必要な検証、失敗時の報告、client 検証の分担は [AGENTS.md](../AGENTS.md) に従う。

現在の GameTest は `gametest.runtime` の実行構成チェックのみで、標準 / Irons / Create の MOD ロードと別構成からの混入を検証する。独自コンテンツは未実装であり、機能・連携動作の保証は追加実装と対応する挙動テストで行う。

## 1. 検証するもの

実プレイで起きる不具合を検出できる処理結果、状態遷移、Minecraft・依存 MOD・データとの接続を優先する。

- アイテム使用の成立・拒否、命中、ダメージ、弾薬・耐久値等の実際の消費を確認する。
- 装備・交換・解除、modifier の適用、処理の開始・中断・終了後の結果を確認する。
- 保存・読込、旧データの復元、アイテムの返却など、既存資産の保護を確認する。
- レシピ選択、タグ判定、登録された定義の利用先への接続を確認する。
- 所有権、権限、射程、設置・破壊許可、消費の重複防止など、server が守る制約を確認する。

すべてを通常のプレイヤー操作から再現する必要はない。検出したい不具合に必要な経路を通し、直接呼び出し、イベント経由、実通信、client 操作のどこまでを確認したかを明確にする。Codec の往復だけで実通信を、演出状態の計算だけで描画を確認済みとしない。

入力を消費したことや要求を受け付けたことを示す戻り値だけで、操作の成功を判定しない。失敗時にも同じ戻り値を返す経路では、生成物、消費、ダメージ等、その操作の成立を識別できる結果を確認する。

禁止設定や許可リストは、判定 helper だけでなく実際の利用入口との接続を確認する。保存後の設定変更による拒否、拒否時の資源・状態の維持、設定を戻した後の利用成功を区別する。別機能の独立した設定まで影響しないことも必要な境界として扱う。

## 2. 維持・書き換え・統合・削除・移動の判断

テスト件数の維持・増加や一定件数までの削減を目的にしない。各テストについて次を確認する。

1. どんな不具合が起きると失敗するか。
2. 起動時チェックや既存テストでも同じ不具合を検出できるか。
3. 正常な仕様変更、乱数、配置、実行順序によって不要な失敗が起きないか。
4. GameTest の world や対象 MOD が本当に必要か。

| 判断 | 基準 |
| --- | --- |
| 維持 | 独立した不具合や重要な境界条件を検出する。 |
| 書き換え | 守りたい挙動は重要だが、観測方法が弱い、実装に追従するだけ、または不安定である。 |
| 統合 | 同じ処理経路と故障原因を重複して検証しており、差分をケースとして表現できる。 |
| 削除 | 定数の転記や、他の検証と保証範囲が重なるだけである。 |
| 移動 | 機能の所属と配置が合わず、検証の責務に沿ったクラス・パッケージへ移す。 |

テスト名だけで削除を決めない。定数確認と挙動確認が混在する場合は、不要な assertion を除き、必要な処理結果を残す。統合時も無関係な検証を巨大な一件へ集約しない。失敗したケースが診断文字列から分かり、各ケースが独立した状態で実行できるようにする。

同じ helper や同じ最終結果でも、利用入口・状態遷移・故障原因が異なる検証は重複とは扱わない。資源不足と必要量ちょうど、手動取消と期限切れ、対象や設定による固有分岐を維持する。拒否の検証では受入れ可能な対照も残し、処理が常に失敗しているだけの成功を防ぐ。

入力をすべて残す統合では、登録数が減っても処理量や実行時間が減るとは限らない。非同期ケースを順番に待つ変更や大きな fixture 再設計が必要になる場合は、診断・保守の改善に見合うか判断する。

ケースをループする共通 helper は、各ケースの内部で `helper.succeed()` を呼ばない。すべてのケースの検証が完了してから入口で成功を通知する。非同期ケースでは、観測対象・生成物・後片付けの混在も防ぐ。

保存復元の検証では、保存前の正規化直後と復元・修復後の両方で必要な結果を確認する。読込時の修復が保存前の不具合を隠す可能性があるため、復元後の成功だけを理由に保存前の assertion を削除しない。

削除・統合では、失う検証と残る検出経路、または検証不要と判断した理由を作業報告や PR 等で簡潔に説明する。恒久的な全件対応表は要求しない。

### 定数・getter・登録

耐久値、レアリティ、光量、演出の強度、既定のバランス値など、設定値を getter で読み返して完全一致を要求するだけの検証は原則追加しない。

完成品の個数、実際の消費量、ダメージ、装備後の補正量など、守りたい処理結果の数値は検証してよい。特定の定数自体を固定する必要がある場合は、その値が変わると起きる不具合と固定する理由を示す。

コンテンツ総数や単純な登録存在の網羅確認を増やさない。起動成功だけでは保証できないレシピ選択、タグ解決、登録先との対応は確認する。必須データの lookup 失敗を `ifPresent` 等で無言に省略せず、そのデータを使った処理結果まで検証する。

静的な tooltip キーや順序は代表ケースと必要な境界へ絞る。設定による表示分岐、エラーの内容と引数、保存状態の反映、表示データの読取がアイテムの状態を変更しないことは独立した挙動として扱う。

### 装備・属性・保存の境界

属性 modifier の定義確認だけで終えず、実際の装備処理後の entity の属性値を優先する。正しい部位、交換・再装備での非重複、解除時の復元、必要な組み合わせを確認する。

共通実装は代表装備と境界条件へまとめられるが、独自 override や異なる装備経路まで無条件に代表一個へ置き換えない。期待値を製品実装から再計算するだけにせず、加算・基礎値への乗算・最終乗算の違いを検出でき、上限への張り付きで差が消えない条件を選ぶ。

FakePlayer 等の更新上の制約を踏まえ、必要な装備更新経路を通す。軽量 mock がすべての構成で使えるとは仮定せず、必要に応じて接続付き ServerPlayer と `doTick()` を使う。world 登録済み player と未登録 player、手動更新と通常更新を区別し、イベント順や cache の有効期間を準備に明示する。接続等の資源は失敗時も解放する。

調整ルール、保存形式、個別装備の効果、メニュー操作は失敗原因が異なるため、独立した準備と検証に分ける。候補一覧や受入れ判定だけでなく、実際の適用・保存、拒否後の状態維持、取外しまで必要な経路を通す。

旧形式の読取・最初の変更による移行・未変更部分や未知の付随データの維持を分けて確認する。現在は新規追加できない内容も、保存済み資産として読取・取外しを保証する。旧データの fixture を新規受入れ API へ一律に置き換えない。

## 3. クラスとパッケージ

GameTest は `jp.aquafactory.artificesassorite.gametest` 配下を基本とし、機能領域と必要な個別機能で分ける。初めから全分類を作らず、実装した機能に合わせる。

- 型の種類や `GameTests` / `Scenarios` という役割だけで全機能を分断しない。
- 特定機能の optional MOD 連携は機能の近くへ置いてよい。複数機能にまたがる連携や外部 API 専用の補助処理は `integration.<mod>` 等へまとめる。
- 行数だけの機械的な分割や厳密な行数上限は設けない。目的・準備・観測・後片付けを追いやすくする。
- 単純なテストは入口クラスに直接実装してよい。入口とシナリオの二段構成を一律に強制しない。
- fixture、定数、観測、後片付けは機能内へ閉じ、複数機能で実際に使うものだけを共通化する。`support` 等に新しい巨大クラスを作らない。
- 配置の都合だけで製品コードの可視性を広げない。観測 helper 自身の誤りが偽陽性を生む場合は、その前提を保証する小さなテストを残してよい。

移動時は探索・登録、アノテーション、template、batch と前後処理、実行フィルター、jar 除外を確認し、重複登録・登録漏れを防ぐ。配置整理と削除・期待値変更は可能な範囲で差分を分ける。パッケージ移動だけでプロファイルの対象や外部型の読込境界が変わるとは扱わない。

## 4. 実行環境と依存 MOD

機能・計算の自動テストは原則 GameTest にまとめ、各 `runGameTestServer...` を対応構成のテスト一式の入口とする。純粋計算も world 状態を参照しない独立した GameTest とし、明示的な入力や時刻で確認する。

JUnit 等は計算部分だけを高速に繰り返す必要が明確になった時点で再検討する。その際も全件実行の入口から漏れない方法と運用負担を合わせて判断する。

Iron's Arms 'n Artifice / GeckoLib / Iron's Lib を標準構成に含める。Iron's Spells 'n Spellbooks / Iron's Gems 'n Jewelry は開発用 Irons 構成のみへ追加し、本 MOD の必須・任意依存には含めない。Create は任意依存として専用構成で確認する。必須 MOD のロード確認だけの重複検証は増やさず、機能追加時は実際に利用する API・登録・データとの接続を確認する。

optional MOD 構成を追加する場合は、要求 MOD が読み込まれていることを確認し、連携処理を通らず成功するのを防ぐ。対象 MOD 不在で成功として省略するテストは連携検証済みと数えない。不在時に外部型を読み込まず起動できることは別の保証として残す。

件数を報告する場合は登録総数・必須数・任意数・省略ケースを区別する。成功ログの件数だけから必須数や実際に通った連携ケース数を推定しない。既知の非互換の観測・上流修正検知の任意テストは通常の互換性保証と分け、flaky な必須テストの一括任意化で済ませない。

## 5. 安定性と後片付け

重要な挙動を検証する flaky テストは実行条件と観測方法を改善する。リトライ・timeout の増加や `required = false` 化だけで解決したことにしない。

- entity 全体の AABB、標的、移動経路、投射物の広がりを template と chunk の tick 範囲へ収める。実行回数で増える static counter を高度分離に使わない。
- helper の相対座標と Level 等の絶対座標を区別し、直接 API の入口で変換する。別テストが world 原点付近を共有する状態を作らない。
- `addFreshEntity` 成功、参照保持、chunk 読込、UUID 検索、空間検索、entity-ticking は別の状態として必要な前提を確認する。手動 `tick()` は world 登録や他 entity の更新を代行しない。
- 自分が生成した個体やイベントを識別する。周辺の同種 entity の総数を代替にせず、近隣テストのドロップ・攻撃等を誤観測しない。複数対象は総数だけでなく個体ごとの結果を確認する。
- 一時 entity は生成・登録を先に確認して自然な終了・取消後の解放を観測する。最終的な空集合だけでは未生成を検出できない。強制的な後片付けで解放漏れを隠さない。
- config・共有状態は変更前の値へ復元し、listener・entity・mock 接続・packet buffer は成功・失敗・timeout の各経路で解放する。batch 分離だけに依存しない。
- AI、天候、日光、物理移動は検証対象と環境ノイズを区別する。tick していないだけで成功する偽陽性にも注意する。
- 有限回の乱数試行で特定結果が必ず出ることを要求しない。不変条件を確認するか出目・候補選択を制御する。固定 seed だけで解決したとせず、復元できない world 共有乱数の変更を避ける。
- 非同期処理には完了条件と期限を設ける。二重ヒットや再消費等の否定条件は必要な観測期間を維持し、同じ観測方法の肯定ケースも用意する。
- 準備・操作を繰り返し評価される成功 callback へ入れない。同期処理は一度だけ操作・assert し、非同期処理は待機中に観測する。`succeedIf` の時刻条件も踏まえ、単純な待機 API の置換で不具合を隠さない。
- 診断は対象・位置・段階・経過 tick・期待値と実測値を英語で示す。命中失敗では実際の命中先、生存・削除状態、UUID・空間検索、chunk 状態も必要に応じて記録する。

消費資源は setter に渡した値だけでなく上限適用後の実値を確認し、目的の分岐へ到達する準備にする。メニューでは入力の処理可否・周辺条件・player 登録と、実際の候補・完成品を確認する。属性倍率の比較へ命中数の乱数を混ぜず、命中と補正を別に検証する。

再実行で成功しても原因が解消したとは判断しない。同じ source・プロファイル・実行対象での追加実行と、fixture・製品コード・期待値を変えた後の実行を区別する。省略を成功回数に含めず、距離・期限・拒否境界を緩めて安定化したことにしない。

## 6. 整理の進め方

対象範囲と終了条件を決め、配置整理、不要な検証の削減、観測方法の改善、実行先の変更を区別する。一度に全機能を移動したり共通 helper を全面再設計したりしない。採用した変更の検証が済んだところで区切り、旧形式が残ることだけを理由に整理を続けない。

機能別の棚卸し文書は必要な期間に限定する。共通の判断基準・教訓は本書へ移し、件数台帳や全件対応表を常設しない。整理後は登録漏れと重要な検出経路を確認し、AGENTS.md に従う検証と必要な client 確認の引き継ぎを行う。
